Step 1 — Current UI Analysis

Where the product stands today

The current build is a competent, mobile-first dark dashboard. It has genuine strengths — but reads more like a well-made side-project than a premium tool. Here's the honest audit.

✅ Strengths

  • Clean single-column mobile layout with a clear visual spine
  • Strong typographic hierarchy — big hero number, confident weights (820–880)
  • Sensible provider color-coding (Jolt / Matty / Chargefox / Supercharger)
  • Thoughtful details: safe-area insets, fixed tab bar, bottom-sheet modal, empty states
  • Consistent 8/14px radius system & reusable metric cards

⚠️ Weaknesses

  • Dark-only — no light mode; feels dim and dated for a data tool
  • Low-opacity white-on-navy surfaces = muddy contrast, weak card separation
  • Single-hue indigo glow does a lot of work; little depth or accent variety
  • Letter-glyph provider marks (J/M/C/S) read as placeholder, not brand
  • Flat 8px radius + one shadow token = little tactility or hierarchy of depth
  • No micro-interactions beyond a 1px hover lift; charts feel generic
  • Version-footer & "EV Command" eyebrow compete with real content

Step 2 — Competitive Benchmarking

What premium looks like in this category

18 leading products across EV charging, energy/solar monitoring, and fintech-grade tracking. The pattern is consistent: bright, high-contrast light UIs, one confident accent, real depth, animated data, and obsessive spacing.

ProductCategoryWhat makes it read as premiumSteal this

🎨 Color systems

The best use a near-white canvas, one saturated accent, and 2–3 tints of it for states — not six competing hues. Semantic greens/ambers stay reserved for status.

✨ Depth & motion

Layered soft shadows, 16–24px radii, and micro-interactions: number count-ups, animated donuts/sparklines, spring-eased toggles. Data feels alive, not static.

🔤 Typography

Tabular-figure numerics, a display face for hero metrics (or heavier Inter), and disciplined type scale. Numbers are the hero — they treat them like it.

Data Requirement — Supabase Integration

Live data: migrate, add & sync, export

Today all 249 sessions live in a static ev_data.json bundled into the build. Here's how to move to a real backend that meets all three requirements — with mockups of how each looks in-app.

Requirement 1

Migrate JSON → Supabase

Seed a charging_sessions table with the existing 249 rows via a one-time import script. Source of truth moves from the bundle to Postgres.

Requirement 2

Add data + live sync

An "Add session" sheet writes to Supabase and the UI updates instantly — optimistic insert, then realtime confirmation across devices.

Requirement 3

Export to CSV

One tap exports the full (or filtered) ledger to an Excel-ready CSV, generated client-side and downloaded — no server round-trip needed.

Recommended implementation

Direct supabase-js from the client with Row-Level Security — no custom backend to maintain. A tiny data layer replaces the static import so the rest of the app barely changes.

// src/data/sessions.ts — replaces the static JSON import
import { createClient } from '@supabase/supabase-js'
const db = createClient(URL, ANON_KEY)

// read
const { data } = await db.from('charging_sessions')
  .select('*').order('date',{ascending:false})

// add + optimistic sync
await db.from('charging_sessions').insert(newSession)
db.channel('sessions').on('postgres_changes',
  {event:'*',schema:'public',table:'charging_sessions'},
  refresh).subscribe()
